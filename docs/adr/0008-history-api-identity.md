# History API ownership and online account identity

`/api/history/*` lives in Expo API routes alongside Better Auth. Every route resolves its caller through `auth/server/history-user.ts` and scopes reads and writes to that verified account; user IDs in uploaded hand records are claims, never authorization. Web sends its browser cookie and native uses Better Auth's SecureStore cookie, following the existing Wallet request path.

Colyseus verifies the Better Auth session token at matchmaking through the server-configured `AUTH_API_URL` (the Expo API origin; HTTPS in production). Better Auth's bearer plugin validates the same session without sharing its database credentials or signing secret with the room server. Table joins refresh the client session first, anonymous/expired/revoked sessions fail, and the verified user ID is kept only in the room's server-side seat binding. Reconnection retains that original account for the held seat; a fresh join revalidates credentials. Account switching does not transfer an existing seat to another account.

An account holds at most one seat per table: a second join by a seated account is refused (409), and `hand_seat` is unique on `(hand_id, user_id)`. History membership, ranked play and buy-ins are per account, so one account in two seats would make each of them ambiguous. Smokes and load tests therefore sign in a distinct seeded account per seat.

The server needs the auth service available for new joins. Rollout order follows from that: the Expo API with the bearer plugin ships before the room server that verifies tokens, and the room server needs `AUTH_API_URL` in production. In development, a Metro that proxies `/api/*` to a hosted backend (`API_PROXY`) verifies against that backend, so table joins only work against an API that already has the plugin. History reads/uploads (STO-460/STO-458) must use the resolved caller ID for ownership and membership checks; this decision establishes that identity boundary without implementing those endpoints.
